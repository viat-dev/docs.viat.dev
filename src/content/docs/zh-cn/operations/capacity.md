# 容量规划与调优

不存在跨硬件的统一吞吐指标,也没有笼统的 HA 保证。容量取决于**你的脚本、
依赖、负载、数据库、对象存储与部署限制**。分工:主机/容器运维管资源上限,
开发者管脚本预算与幂等;增加并行前两边要协调。

## 建预算,而不是一个并发数字

| 组件 | 默认/约束 | 预算含义 |
| --- | --- | --- |
| 共享热池 | 16 槽、队列 32、等待 5 秒 | Python/TypeScript 短任务进程与导入;独占槽**另外**增加。 |
| 长任务通道 | 8 并发、同步等待 5 秒 | 一次性进程可占内存数分钟;持久队列可等待而不被拒。 |
| 流式通道 | 8 并发、等待 30 秒 | 长期占用连接/进程;慢消费者/代理缓冲会钉住资源。 |
| 异步在途 | 每进程 128 | 独立准入限制,**不是**"128 份保证 CPU"。 |
| 持久队列 | 每键等待 1000、纯延迟 100000 | 行保留请求/身份/目标;**队列年龄与深度同样重要**。 |
| 平台 PostgreSQL | 每进程池 10 + 其他连接 | 为通知/后台/管理/备份预留;没有受支持的池大小变量。 |
| 业务库缓存池 | PostgreSQL/MySQL 通常每资源/进程 8 | 乘以活跃资源数与实例数,同时算上数据库自身额度。 |
| WebSocket | 每进程 10000、队列 32、消息 64 KiB | 是**协议上限**不是实测容量;内存/FD 可能先到顶。 |
| 响应缓存 | 默认每进程权重预算 64 MiB | 另有元数据/分配器开销;Redis 也要独立规划。 |
| 上传/构建/日志 | spool、uv、Cargo target、产物与日志 | 磁盘/inode/IO 分开预算;产物 LRU 不限制 Cargo target。 |

精确的解析、覆盖与作用域见[运行时](../configuration/runtime.md)、
[存储](../configuration/storage.md)、[网络](../configuration/network.md)。
注意:一次性进程/进程内 SQL/资源调用/工作流 fan-out **不都**受共享池限制
——共享池不是万能的进程/查询总闸。

## 建立代表性基线

在隔离的预生产项目,用脱敏真实输入与相同解释器/镜像类别,分别测量:

1. 冷依赖/构建与热执行——只测热路径会掩盖发布/首调用故障。
2. 短同步、长异步、流式、嵌套/并行工作流与数据库密集目标。
3. 端到端 p50/p95/p99、队列等待/年龄、拒绝/超时率、CPU、RSS/峰值、
   PID/线程、FD、数据库连接/锁、磁盘/inode 增长。
4. 依赖/缓存/收集器失败与重启恢复。未经明确批准不调用付费或真实
   provider。

在资源耗尽**前**停止;记录负载、版本、限制与实测值。每次只改一组控制,
用同一负载复测;为重启、后台清理与突发留余量。**一次请求成功不等于
可持续容量。**

## 容器与编译约束

- Compose/部署脚本示例的 **512 PID、4g 内存**只是起点,不适合所有负载。
- Docker 的 PID 额度**包含线程**;Cargo/rustc 产生的线程远多于"几个进程"。
  编译节点通常要单独实测预算与受控的 `CARGO_BUILD_JOBS`;把编译竞争移出
  低延迟执行节点可能有帮助,但**不自动构成**受保证的 HA 拓扑。
- 失控分配或 fork 可以杀死整个容器:保留内存/PID 限制与安全约束,不要用
  "永久无限资源"或 `seccomp=unconfined` 来修。不同的 worker UID 不是每脚本
  cgroup 沙箱。FD 限制应在测量后由服务管理器/容器主机配置——**没有**可
  随意发明的 Viat 环境变量。

实际 Docker 主机上的**只读观察模板**(未执行):

```sh
docker stats --no-stream viat-server
docker inspect --format '{{.State.Status}} {{.RestartCount}}' viat-server
docker logs --since 15m viat-server
df -h
df -i
```

日志私下查看,容器名换成实际部署的;这些命令不自动测定、也不修改生产
容量。

## 多节点行为与限制

- 共享 PostgreSQL 节点协调:已发布路由刷新、认领/租约与部分后台任务。
  仍然本地的:热 worker、默认响应缓存、端点限流桶。
- 共享 Redis 缓存与限流分别启用;限流故障退回本地,缓存故障按 miss 处理。
  共享产物/依赖缓存要显式持久化,并协调工具链/架构。本地文件监听/存储
  **不会**自动复制。
- 节点间应一致:主密钥/JWT、公共 URL、后端与兼容产物。合计整个集群的
  数据库/资源连接与外部配额;按真实拓扑验证负载均衡、流式/WebSocket 与
  节点中断。
- 就绪探针**刻意**不因"数据库池连接都忙"摘除节点——`pool:saturated`
  可以返回 200;所以 **readiness 不能代替负载监测**。
- 锁/租约/心跳减少重复工作,不承诺 exactly-once 或零中断;数据库/网络
  分区与已提交外部动作仍靠幂等。部署脚本是强制替换单容器,**不是** HA
  滚动编排器。

## 对因调参

| 症状 | 先做什么 |
| --- | --- |
| READY 超时 | 修包、缓存、工具/源并持久化预热——不是先调执行超时 |
| 503 等待 | 查共享/长任务/流式通道、时长与下游限制;不要只扩所有队列 |
| 数据库池/锁等待 | 降低 fan-out、修查询/事务、预留容量;加副本可能更糟 |
| 大输出/上传占内存 | 用受支持的流式接口,保留 helper/entry 限制;缓冲增大 × 并发会放大 |
| 队列增长 | 限生产者、合理分工、优先幂等恢复,监测**最老年龄**;更多积压 ≠ 更高吞吐 |

调参后若错误/延迟/资源恶化:恢复基线、留试验记录,并在新限制下复核
[备份](backup-restore.md)、[告警](alerts.md)与[升级](upgrades.md)。
